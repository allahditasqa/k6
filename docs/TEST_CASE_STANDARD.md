# Test case standard

Every module in this repository is documented in the same format, in simple English, so that anyone can read, run and review a case. It follows the standard used in my other automation repositories (Playwright, Cypress).

## 1. Where things live

| Item | Location | Example |
| --- | --- | --- |
| Test case document (source of truth) | `docs/test-cases/<module>.md` | `docs/test-cases/smoke.md` |
| **Master CSV** (regression list, generated) | `docs/test-cases/<module>.csv` | `docs/test-cases/smoke.csv` |
| Automation code | `scripts/*.js` (k6 scripts, one scenario per file) | |
| Run CSV (result of one run, with the real result) | `reports/<module>/<Module Name> test cases <DD-MM-YYYY>_<HH-mm-ss>.csv` | |
| Report of one run | `reports/<module>/<Module Name> test <DD-MM-YYYY>_<HH-mm-ss>.html` | |
| History of all runs | `reports/index.html` and `reports/history.json` | |

One module = one document + one master CSV + one report.

## 2. Test case ID
`TC_<MODULE>_<NN>`, for example `TC_SMOKE_02`. An ID is never reused or renumbered.
The ID is written as a comment next to the threshold in the script: `http_req_duration: ["p(95)<1500"], // TC_SMOKE_02`. A performance test case is one threshold of a scenario.

## 3. Title rule
A title is one complete sentence that says **what is done** and **which data is used**, for example:
`Smoke: 95% of the requests answer in under 1500 ms`.
It is the same in the document, in the code, in the CSV and in the report.

## 4. Columns of every test case table (never change)

| Column | Meaning |
| --- | --- |
| ID | `TC_<MODULE>_<NN>` |
| Title | one sentence, see rule 3 |
| Priority | `High` (core behaviour; the product is not usable if it fails), `Medium`, `Low` (cosmetic) |
| Type | Performance |
| Preconditions | what must be true before step 1 (`None` if nothing) |
| Test data | the exact values used |
| Steps | short numbered action sentences: `1. Send ... 2. Check ...` |
| Expected result | clear and checkable, quote exact values |
| Automated in | `<path of the test file>::<test name>` |

Only **automated** cases are written down. A manual idea that is not automated does not belong in these documents.

## 5. Writing rules
1. Simple English, active voice: "Send GET /posts", not "GET /posts should be sent".
2. One test case checks one behaviour.
3. Quote exact values and text.
4. A test case is never silently changed: update the document, run `node tools/docs.js csv`, review the diff.

## 6. Master CSV and the traceability check
- The master CSV is generated from the documents: `node tools/docs.js csv` (Node 18 or newer, no packages needed). Edit the document, never the CSV.
- Rows that did not change keep their `Last Updated` date, so the CSV shows what changed and when.
- `node tools/docs.js check` fails when the documents, the master CSVs and the test code drift apart: an ID that is documented but missing in the code, an ID in the code that is not documented, a duplicate ID, a missing test file, or an out-of-date CSV. It runs in CI.

## 7. Run results
Every run of the suite writes a new module-wise report and run CSV under `reports/` (see the README). The run CSV repeats the case (steps, expected result) and adds the **real** result, status and duration of that run. Reports are generated by the test run itself and are never edited by hand.
